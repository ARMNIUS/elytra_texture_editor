# Разделение на Pixel Studio и Minecraft Texture Studio

Статус: предложение к обсуждению. Ветка: `split-sys`.
Базовая версия: 0.12.0 (один Tauri-апп, монолитный `App.tsx`, фиксированный холст 64×32).

## 1. Цель

Разделить продукт на два самостоятельных приложения, использующих общее ядро:

1. **Pixel Studio** — универсальный пиксель-арт/спрайт-редактор: произвольные размеры холста, слои, выделение, инструменты, палитры, анимация кадров в перспективе. Без Minecraft-кода и без `three.js`/`skinview3d` в бандле.
2. **Minecraft Texture Studio** — то же ядро плюс плагин Minecraft: модели, UV-развёртки, скины, элитры, плащи, 3D-просмотр и покраска по модели.

Плагин не должен быть отдельной копией редактора. Он расширяет ядро через стабильный API: добавляет типы документов, панели, инструменты, импорт/экспорт, 3D-вьюпорт и UV-оверлеи.

## 2. Рекомендуемая архитектура

### 2.1 Один репозиторий, два приложения

Не делать два форка. Использовать npm workspaces (без смены пакетного менеджера) и общее ядро:

```text
apps/
  pixel-editor/          # React + Vite + Tauri: только универсальный редактор
  minecraft-editor/      # React + Vite + Tauri: ядро + minecraft-плагин
packages/
  core/                  # документ, растр, история, выделение, команды, проект
  editor-ui/             # Win9x-оболочка, канвас, общие панели
  plugin-api/            # интерфейсы плагинов и реестры вкладов
  plugin-minecraft/      # модели, UV, 3D, импорт/экспорт Minecraft
  model-formats/         # bbmodel / Bedrock geometry / Java block-item JSON
  shared/                # color, shapes, files, shortcuts
src-tauri-shared/        # общий Rust-слой: диалоги, чтение/запись
docs/
```

Оба приложения собираются из одного коммита, но имеют разные `productName`, `identifier`, иконки, file associations и установщики. Общие пакеты не дублируются.

### 2.2 Два продукта, а не один режим

Рассматривались два варианта:

- **A. Один апп с режимами «спрайт / Minecraft»** — дешевле в поддержке, но Minecraft-зависимости остаются в бандле, а пользователь просил именно разделение.
- **B. Два аппа на общем ядре** — рекомендуется. Pixel Studio остаётся лёгким и не содержит Minecraft-ассетов; Minecraft-апп подключает плагин и модельтные форматы.

### 2.3 Плагин: статический в v1, динамический позже

Для Tauri динамическая загрузка сторонних JS-плагинов — это CSP, версии API, подписи и риск выполнения чужого кода. Поэтому:

- **v1:** плагин — workspace-пакет, подключаемый на этапе сборки. В UI он выглядит как включаемая возможность/workspace, но код проверен и входит в установщик.
- **v2 (после стабилизации API):** менеджер плагинов с папкой `%APPDATA%/PixelStudio/plugins/<id>/`, манифестом, проверкой `apiVersion` и подписи. Загружать только доверенные плагины; без доступа к произвольному DOM и внутреннему состоянию ядра.

Такой путь даёт «плагинную» архитектуру без преждевременной небезопасной инфраструктуры.

## 3. Ядро редактора

### 3.1 Произвольные размеры холста

Сейчас 64×32 зашиты примерно в 87 местах (`TEXTURE_WIDTH`, `TEXTURE_HEIGHT`, `TEXTURE_PIXEL_COUNT`) в `texture.ts`, `layers.ts`, `transform.ts`, `project.ts`, `TextureCanvas`, `ElytraViewer` и тестах.

Целевая модель:

```ts
type Raster = { width: number; height: number; pixels: string[] };
type Layer = { id: string; name: string; visible: boolean; opacity: number; pixels: string[] };
type Document = {
  id: string;
  name: string;
  width: number;
  height: number;
  layers: Layer[];
  activeLayerId: string;
  selection: SelectionRect | null;
  extensions: Record<string, unknown>; // данные плагинов, ядро их не интерпретирует
};
```

Правила:

- длина `layer.pixels` всегда `width * height`;
- все утилиты (`floodFill`, `paintPoints`, `copyRegion`, `transform`, `shapePoints`) принимают размеры/`Raster`, а не глобальные константы;
- `TextureCanvas` получает `width`/`height` пропсами;
- выделение, копирование, вставка, трансформации и экспорт клипаются по размерам документа;
- новый проект: диалог с шириной/высотой, пресетами (16, 32, 64, 128, 256, 512), прозрачным/белым фоном;
- лимит v1 — 1024×1024 (дальше — отдельная оптимизация истории);
- зум/центрирование/шахматка/сетка работают для любого размера.

### 3.2 История и производительность

Сейчас undo хранит полные копии слоёв. Для 64×32 это нормально, для 512×512 и нескольких слоёв — тяжело.

Этапы:

1. Сначала сохранить текущий snapshot-подход, но ограничить разрешение и число шагов.
2. Затем перейти на **дельта-историю по изменившимся регионам** (`HistoryPatch { layerId, rect, before, after }`), особенно для кисти, заливки и трансформаций.
3. Для больших холстов — тайлы или сжатие снимков; это отдельный этап после split.

### 3.3 Ядро не знает о Minecraft

В `packages/core` не должно быть:

- `skinview3d`, `three`, `defaultElytraPixels`, `steve.png`;
- UV-разметки элитр и модели;
- `.mts`-специфики, кроме миграции в плагине.

Ядро знает только: растр, слои, выделение, историю, палитру, инструменты, команды, настройки и формат проекта с `extensions`.

## 4. Plugin API (v1, набросок)

```ts
interface EditorPlugin {
  id: string;
  name: string;
  version: string;
  apiVersion: 1;
  activate(context: PluginContext): void | Promise<void>;
  deactivate?(): void;
}

interface PluginContext {
  commands: CommandRegistry;
  menus: MenuRegistry;              // пункты меню с областью видимости
  panels: PanelRegistry;            // левая/правая/нижняя панель
  documentTypes: DocumentTypeRegistry;
  overlays: OverlayRegistry;        // SVG/2D-оверлеи над канвасом
  previews: PreviewRegistry;        // 3D/иные вьюпорты
  importers: ImporterRegistry;
  exporters: ExporterRegistry;
  settings: PluginSettings;
  events: EventBus;
  storage: PluginStorage;           // только своё пространство имён
}
```

Ключевые принципы:

- ядро предоставляет **слоты**, плагин — вклады (contributions);
- плагин не мутирует чужие документы напрямую, только через команды/сервисы;
- данные плагина живут в `document.extensions[pluginId]` и сохраняются как непрозрачный JSON;
- API версионируется; несовпадение `apiVersion` — плагин не активируется;
- ошибка плагина не роняет редактор: изоляция панели/команды и сообщение в статусе.

## 5. Minecraft-плагин

### 5.1 Что значит «все модели»

Важное ограничение: в Java Edition модели сущностей заданы **кодом**, а не JSON-файлами. Нельзя автоматически «поддержать все модели» только чтением ресурспака. Реалистичная поддержка:

| Источник | Поддержка | Комментарий |
|---|---|---|
| Blockbench `.bbmodel` | да, v1 | кости, кубы, UV, анимации |
| Bedrock geometry `.geo.json` | да, v1 | entity/block/armor geometry |
| Java block/item JSON | да, v2 | блоки/предметы, data-driven |
| Java entity | курируемая библиотека / конвертация | код, а не данные; поддержка по версиям |
| Player/skin/elytra/cape | встроено | текущий `ElytraViewer` как один из адаптеров |
| Анимации | Bedrock/bbmodel, позже | Java-анимации код-driven |

«Полная поддержка» в плане означает: **любая модель, представимая в общем формате костей/кубов/UV**, импортируется и редактируется. Автоматический экспорт всех сущностей из игры — отдельная задача с юридическими и версионными рисками.

### 5.2 Общий формат модели

```ts
type ModelBone = {
  id: string;
  parentId: string | null;
  pivot: [number, number, number];
  rotation: [number, number, number];
  cubes: ModelCube[];
};
type ModelCube = {
  origin: [number, number, number];
  size: [number, number, number];
  pivot: [number, number, number];
  rotation: [number, number, number];
  inflate: number;
  uv: Record<'north'|'south'|'east'|'west'|'up'|'down', [number, number, number, number]>;
};
type ModelAsset = {
  id: string;
  name: string;
  textureWidth: number;
  textureHeight: number;
  bones: ModelBone[];
  animations?: ModelAnimation[];
};
```

Один рендерер на `three.js` строит сцену из `ModelAsset`. `skinview3d` можно оставить только как адаптер плеера/элитр, но лучше постепенно заменить общим рендерером, чтобы не было двух 3D-стеков.

### 5.3 UV и покраска

- Для каждой грани куба хранится UV-прямоугольник.
- Raycast по треугольникам даёт UV-координату; она переводится в пиксель текстуры с учётом её реальных размеров.
- 2D-оверлей UV рисуется по тем же данным, а не по захардкоженной разметке элитр.
- Поддержка нескольких текстур у одной модели (skin + elytra + cape + armor) через `textureSlots`.
- Режимы: «текстура», «UV», «3D», «split»; набор инструментов общий, но 3D-рисование включается только для модельных документов.

### 5.4 Документы Minecraft

Документ Minecraft — это **workspace**:

```ts
type MinecraftExtension = {
  modelId: string;
  textureDocuments: Array<{ slot: string; documentId: string }>;
  activeTextureSlot: string;
  pose?: Record<string, [number, number, number]>;
  animationId?: string;
};
```

Текстуры остаются обычными документами ядра (skin 64×64, elytra 64×32, item 16×16, atlas любого размера). Это позволяет открывать их во вкладках и переиспользовать все инструменты.

### 5.5 Импорт/экспорт

- Импорт `.bbmodel`, Bedrock `.geo.json`, Java block/item JSON.
- Импорт текстур PNG с привязкой к слотам.
- Экспорт PNG/атласа.
- Экспорт resource pack: `assets/<namespace>/textures/...` + `models/...` + `sounds` не нужны.
- Импорт старого `.mts` — через миграцию в Minecraft-плагине.

## 6. Форматы проектов

### Пиксель-арт

Новый формат ядра, например `.pxa` (или `.pxproj`):

```json
{
  "format": "pixel-studio-project",
  "version": 1,
  "name": "sprite",
  "width": 64,
  "height": 64,
  "layers": [],
  "palettes": [],
  "settings": {},
  "extensions": {}
}
```

### Minecraft

Тот же контейнер + `extensions.minecraft`:

```json
{
  "format": "pixel-studio-project",
  "version": 1,
  "width": 64,
  "height": 32,
  "extensions": {
    "minecraft": {
      "modelId": "elytra",
      "textureSlots": { "elytra": "layer-doc-id" }
    }
  }
}
```

Это позволяет открывать файл в обоих приложениях: Pixel Studio покажет текстуру и проигнорирует неизвестное расширение, Minecraft-апп восстановит модель.

### Миграция

- `.mts` v1/v2 (64×32) читается Minecraft-плагином и конвертируется в новый формат;
- ядро не обязано знать `.mts`;
- старые проекты продолжают открываться в Minecraft-редакторе;
- при сохранении старый `.mts` можно оставить как экспорт, но основной формат — новый.

## 7. UI и брендинг

- Общая Win9x-оболочка в `packages/editor-ui`.
- Pixel Studio: документы-спрайты, без вкладок «3D/UV», без Minecraft-панелей; палитра, слои, таймлайн кадров (позже).
- Minecraft Texture Studio: те же вкладки + панель модели, UV, 3D, выбор модели, слоты текстур.
- Плагин добавляет пункты меню «Модель», «UV», «Ресурспак»; при выключенном плагине их нет.
- Настройки: ядро хранит общие, плагин — `minecraft.*`.
- Иконки/имена:
  - `Pixel Studio` — новый идентификатор и иконка;
  - `Minecraft Texture Studio` — текущий бренд/иконка;
  - репозиторий можно оставить один (`elytra_texture_editor`), но это стоит обсудить.

## 8. Сборка и поставка

- `apps/pixel-editor/src-tauri` и `apps/minecraft-editor/src-tauri` с общим Rust-крейтом для файловых диалогов.
- Отдельные `identifier`:
  - `com.armnius.pixelstudio`
  - `com.armnius.minecrafttexturestudio`
- Отдельные установщики NSIS, иконки, file associations:
  - `.pxa` → Pixel Studio
  - `.mts`/`.mcproj` → Minecraft Texture Studio
- CI собирает оба приложения; тег релиза даёт два артефакта.
- Pixel Studio не должен содержать `three`, `skinview3d`, Minecraft-ассеты — проверять размер бандла в CI.

## 9. Дорожная карта

Оценки — для одного разработчика, без полного Java-парка моделей и без анимаций в первом релизе.

### Этап 0. Решения и каркас (2–3 дня)

- Утвердить два аппа и статический плагин в v1.
- Создать npm workspaces, `packages/core`, `packages/editor-ui`, `packages/plugin-api`.
- Перенести чистые утилиты без изменения поведения; тесты остаются зелёными.
- Зафиксировать API плагина v1 в типах.

**Готово, когда:** `npm test` зелёный, оба аппа собираются, текущий функционал не сломан.

### Этап 1. Ядро и произвольные размеры (1–2 недели)

- Убрать `TEXTURE_WIDTH/HEIGHT/PIXEL_COUNT` из ядра.
- `Document.width/height`, `Layer.pixels` валидируется по размерам.
- Все инструменты/трансформации/выделение/экспорт — с размерами.
- Диалог нового проекта: пресеты + произвольный размер.
- Формат `.pxa` v1, миграция текущего `.mts`.
- Тесты на 1×1, 16×16, 64×32, 128×128, неквадратные размеры.

**Готово, когда:** можно создать 128×128, рисовать, сохранить/открыть, экспортировать PNG; Pixel Studio не содержит Minecraft-кода.

### Этап 2. Плагин-хост (1 неделя)

- Реестры команд/меню/панелей/оверлеев/типов документов.
- `PluginHost`, активация/деактивация, изоляция ошибок.
- UI-слоты в оболочке.
- Заглушка `minecraft`-плагина с панелью «Модель» и пустым 3D.
- Тест: отключённый плагин не ломает редактор.

**Готово, когда:** ядро запускается с плагином и без него; вклады плагина появляются/исчезают.

### Этап 3. Minecraft MVP (2–3 недели)

- Общий `ModelAsset` и рендерер на `three`.
- Адаптеры: player/elytra/cape (текущий), Bedrock geometry, Blockbench `.bbmodel`.
- UV-оверлей из модели, покраска по UV.
- Слоты текстур, привязка документов.
- Импорт старого `.mts`, сохранение `.mcproj`.
- Панель выбора модели/текстуры, 3D/split.

**Готово, когда:** открывается старая элитра, импортируется простая Bedrock-модель, краска попадает в правильный пиксель текстуры.

### Этап 4. Расширенная поддержка моделей (2–4 недели)

- Java block/item JSON.
- Курируемая библиотека Java-сущностей (player, armor stand, базовые мобы) с версионированием.
- Анимации Bedrock/bbmodel, позы, предпросмотр.
- Несколько текстур на модель.
- Экспорт resource pack.
- Валидация моделей и диагностика.

**Готово, когда:** пользователь импортирует `.bbmodel`/`.geo.json` без ручной правки; модель и текстуры сохраняются в проекте.

### Этап 5. Два приложения и релиз (1 неделя)

- Два Tauri-аппа, идентификаторы, иконки, установщики.
- File associations, миграция настроек.
- CI на два артефакта, документация.
- Проверка, что Pixel Studio не тянет `three`/Minecraft-ассеты.

**Готово, когда:** два установщика, оба запускаются, старые `.mts` открываются в Minecraft-версии.

### Этап 6. Стабилизация

- Тесты модели/UV/импорта, скриншот-тесты, ручной smoke-test установщиков.
- Оптимизация истории для больших холстов.
- Полировка UX и документации.

**Итого:** около 8–12 недель до двух стабильных приложений с базовыми моделями; полный Java-парк и анимации — отдельный, более длинный трек.

## 10. Риски

1. **«Все модели»** — Java-сущности не data-driven; без курируемой библиотеки/конвертера полного автопокрытия не будет.
2. **Юридические ограничения** — модели/текстуры Mojang нельзя бездумно бандлить в публичный репозиторий. Нужны собственные/лицензированные ассеты или импорт из файлов пользователя.
3. **Производительность** — большие холсты и полные snapshot-истории; нужен лимит и затем дельта-история.
4. **Plugin API** — легко «протечь» внутренностям ядра; версионировать и держать узким.
5. **Два 3D-стека** — `skinview3d` и общий рендерер; лучше один общий, иначе двойная поддержка.
6. **Динамические плагины** — безопасность, CSP, подписи; не делать в v1.
7. **Дублирование UI** — вынести оболочку в `editor-ui`, иначе два аппа разойдутся.
8. **Миграция `.mts`** — старые файлы должны открываться; хранить тесты миграции.

## 11. Что нужно решить до кода

1. **Два отдельных установщика** или один апп с режимами? Рекомендация: два.
2. **«Все модели»**: достаточно ли Bedrock geometry + Blockbench + Java block/item + курируемая библиотека сущностей? Или нужен автоматический импорт из game jar?
3. **Анимации** в первом релизе или позже?
4. **Максимальный размер холста** в v1: 512, 1024 или больше?
5. **Плагины**: только встроенный Minecraft-плагин в v1 или сразу установка сторонних?
6. **Брендинг/репозиторий**: оставляем `elytra_texture_editor` или переименовываем в `pixel-studio`?
7. **Совместимость**: `.mts` остаётся форматом экспорта или только миграцией?

## 12. Первые шаги после согласования

1. Создать workspace-каркас и перенести `utils` в `packages/core` без изменения поведения.
2. Ввести `Document.width/height` и прогнать тесты на нескольких размерах.
3. Определить `plugin-api` типами и сделать no-op хост.
4. Подключить текущий `ElytraViewer` как первый плагин-адаптер, не удаляя функциональность.
5. Только после этого начинать общий модельный рендерер и импорт `.bbmodel`/Bedrock.

Главный принцип: сначала **ядро и размеры**, затем **границы плагина**, и только потом **модели**. Если начать с моделей, разделение придётся переделывать.
