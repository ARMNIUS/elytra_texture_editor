# Разделение на RawSprite и RawSprite Minecraft

Статус: решения согласованы, начинается этап 0. Ветка: `split-sys`.
Базовая версия: 0.12.0 (один Tauri-апп, монолитный `App.tsx`, фиксированный холст 64×32).

## 0. Утверждённые решения

- **Два отдельных приложения**: `RawSprite` (универсальный пиксель-арт) и `RawSprite Minecraft` (ядро + Minecraft-плагин).
- **Максимальный холст**: 2048×2048. История и память оптимизируются под это отдельно.
- **Модели в v1**: только то, что уже есть — player/skin, elytra, cape, текущие 3D/UV-инструменты. Автопарсинг игры и новые форматы моделей не входят в v1.
- **Анимации**: отложены, решение позже.
- **Плагин**: встроенный статический в v1; динамическая установка — после стабилизации API.
- **Имя проекта/репозитория**: `RawSprite`. GitHub-репозиторий переименовывается в `rawsprite` вручную (git не умеет переименовывать remote-репозиторий).
- Предлагаемые имена пакетов: `@rawsprite/core`, `@rawsprite/editor-ui`, `@rawsprite/plugin-api`, `@rawsprite/minecraft`.
- Предлагаемые расширения: `.rsp` для RawSprite, `.mts` остаётся для Minecraft-проектов и миграции.

## 1. Цель

Разделить продукт на два самостоятельных приложения, использующих общее ядро:

1. **RawSprite** — универсальный пиксель-арт/спрайт-редактор: произвольные размеры холста, слои, выделение, инструменты, палитры, анимация кадров в перспективе. Без Minecraft-кода и без `three.js`/`skinview3d` в бандле.
2. **RawSprite Minecraft** — то же ядро плюс плагин Minecraft: модели, UV-развёртки, скины, элитры, плащи, 3D-просмотр и покраска по модели.

Плагин не должен быть отдельной копией редактора. Он расширяет ядро через стабильный API: добавляет типы документов, панели, инструменты, импорт/экспорт, 3D-вьюпорт и UV-оверлеи.

## 2. Рекомендуемая архитектура

### 2.1 Один репозиторий, два приложения

Не делать два форка. Использовать npm workspaces (без смены пакетного менеджера) и общее ядро:

```text
apps/
  rawsprite/          # React + Vite + Tauri: только универсальный редактор
  rawsprite-minecraft/      # React + Vite + Tauri: ядро + minecraft-плагин
packages/
  core/                  # документ, растр, история, выделение, команды, проект
  editor-ui/             # Win9x-оболочка, канвас, общие панели
  plugin-api/            # интерфейсы плагинов и реестры вкладов
  plugin-minecraft/      # модели, UV, 3D, импорт/экспорт Minecraft
  model-formats/         # bbmodel / Bedrock geometry / Java block-item JSON
  shared/                # color, shapes, files, shortcuts
src-tauri-shared/        # общий Rust-слой: диалоги, чтение/запись
docs/
```

Оба приложения собираются из одного коммита, но имеют разные `productName`, `identifier`, иконки, file associations и установщики. Общие пакеты не дублируются.

### 2.2 Два продукта, а не один режим

Рассматривались два варианта:

- **A. Один апп с режимами «спрайт / Minecraft»** — дешевле в поддержке, но Minecraft-зависимости остаются в бандле, а пользователь просил именно разделение.
- **B. Два аппа на общем ядре** — рекомендуется. RawSprite остаётся лёгким и не содержит Minecraft-ассетов; RawSprite Minecraft подключает плагин и модельтные форматы.

### 2.3 Плагин: статический в v1, динамический позже

Для Tauri динамическая загрузка сторонних JS-плагинов — это CSP, версии API, подписи и риск выполнения чужого кода. Поэтому:

- **v1:** плагин — workspace-пакет, подключаемый на этапе сборки. В UI он выглядит как включаемая возможность/workspace, но код проверен и входит в установщик.
- **v2 (после стабилизации API):** менеджер плагинов с папкой `%APPDATA%/PixelStudio/plugins/<id>/`, манифестом, проверкой `apiVersion` и подписи. Загружать только доверенные плагины; без доступа к произвольному DOM и внутреннему состоянию ядра.

Такой путь даёт «плагинную» архитектуру без преждевременной небезопасной инфраструктуры.

## 3. Ядро редактора

### 3.1 Произвольные размеры холста

Сейчас 64×32 зашиты примерно в 87 местах (`TEXTURE_WIDTH`, `TEXTURE_HEIGHT`, `TEXTURE_PIXEL_COUNT`) в `texture.ts`, `layers.ts`, `transform.ts`, `project.ts`, `TextureCanvas`, `ElytraViewer` и тестах.

Целевая модель:

```ts
type Raster = { width: number; height: number; pixels: string[] };
type Layer = { id: string; name: string; visible: boolean; opacity: number; pixels: string[] };
type Document = {
  id: string;
  name: string;
  width: number;
  height: number;
  layers: Layer[];
  activeLayerId: string;
  selection: SelectionRect | null;
  extensions: Record<string, unknown>; // данные плагинов, ядро их не интерпретирует
};
```

Правила:

- длина `layer.pixels` всегда `width * height`;
- все утилиты (`floodFill`, `paintPoints`, `copyRegion`, `transform`, `shapePoints`) принимают размеры/`Raster`, а не глобальные константы;
- `TextureCanvas` получает `width`/`height` пропсами;
- выделение, копирование, вставка, трансформации и экспорт клипаются по размерам документа;
- новый проект: диалог с шириной/высотой, пресетами (16, 32, 64, 128, 256, 512), прозрачным/белым фоном;
- лимит v1 — 2048×2048 (дальше — отдельная оптимизация истории);
- зум/центрирование/шахматка/сетка работают для любого размера.

### 3.2 История и производительность

Сейчас undo хранит полные копии слоёв. Для 64×32 это нормально, для 512×512 и нескольких слоёв — тяжело.

Этапы:

1. Сначала сохранить текущий snapshot-подход, но ограничить разрешение и число шагов.
2. Затем перейти на **дельта-историю по изменившимся регионам** (`HistoryPatch { layerId, rect, before, after }`), особенно для кисти, заливки и трансформаций.
3. Для больших холстов — тайлы или сжатие снимков; это отдельный этап после split.

### 3.3 Ядро не знает о Minecraft

В `packages/core` не должно быть:

- `skinview3d`, `three`, `defaultElytraPixels`, `steve.png`;
- UV-разметки элитр и модели;
- `.mts`-специфики, кроме миграции в плагине.

Ядро знает только: растр, слои, выделение, историю, палитру, инструменты, команды, настройки и формат проекта с `extensions`.

## 4. Plugin API (v1, набросок)

```ts
interface EditorPlugin {
  id: string;
  name: string;
  version: string;
  apiVersion: 1;
  activate(context: PluginContext): void | Promise<void>;
  deactivate?(): void;
}

interface PluginContext {
  commands: CommandRegistry;
  menus: MenuRegistry;              // пункты меню с областью видимости
  panels: PanelRegistry;            // левая/правая/нижняя панель
  documentTypes: DocumentTypeRegistry;
  overlays: OverlayRegistry;        // SVG/2D-оверлеи над канвасом
  previews: PreviewRegistry;        // 3D/иные вьюпорты
  importers: ImporterRegistry;
  exporters: ExporterRegistry;
  settings: PluginSettings;
  events: EventBus;
  storage: PluginStorage;           // только своё пространство имён
}
```

Ключевые принципы:

- ядро предоставляет **слоты**, плагин — вклады (contributions);
- плагин не мутирует чужие документы напрямую, только через команды/сервисы;
- данные плагина живут в `document.extensions[pluginId]` и сохраняются как непрозрачный JSON;
- API версионируется; несовпадение `apiVersion` — плагин не активируется;
- ошибка плагина не роняет редактор: изоляция панели/команды и сообщение в статусе.

## 5. Minecraft-плагин

### 5.1 Модели в v1

В первом релизе Minecraft-плагин **не добавляет новые форматы моделей и не парсит игру**. Он переносит в плагин то, что уже работает:

- игрок / Steve skin;
- элитры;
- плащ;
- текущий 3D-просмотр и покраску по UV.

Этого достаточно для первого разделения: `RawSprite Minecraft` должен вести себя как текущий редактор, но с модельным блоком, изолированным в плагине.

Автопарсинг game jar, Blockbench `.bbmodel`, Bedrock geometry и Java block/item — **следующий этап после стабилизации split**, не v1. Архитектурные точки расширения (`ModelAsset`, `ModelSource`, `textureSlots`) остаются, но реализация форматов откладывается.

### 5.2 Будущие форматы (не входит в v1)

| Источник | Когда | Комментарий |
|---|---|---|
| Blockbench `.bbmodel` | после v1 | кости, кубы, UV, анимации |
| Bedrock geometry `.geo.json` | после v1 | entity/block/armor geometry |
| Java block/item JSON | после v1 | блоки/предметы, data-driven |
| Java entity | после v1 | код, а не данные; нужна курируемая библиотека |
| Анимации | по решению | Java-анимации код-driven; Bedrock/bbmodel — данные |

Будущий общий формат — кости/кубы/UV; текущий `ElytraViewer` можно оставить как специализированный адаптер плеера/элитр, чтобы не переписывать 3D до стабилизации ядра.

### 5.3 UV и покраска

- Для каждой грани куба хранится UV-прямоугольник.
- Raycast по треугольникам даёт UV-координату; она переводится в пиксель текстуры с учётом её реальных размеров.
- 2D-оверлей UV рисуется по тем же данным, а не по захардкоженной разметке элитр.
- Поддержка нескольких текстур у одной модели (skin + elytra + cape + armor) через `textureSlots`.
- Режимы: «текстура», «UV», «3D», «split»; набор инструментов общий, но 3D-рисование включается только для модельных документов.

### 5.4 Документы Minecraft

Документ Minecraft — это **workspace**:

```ts
type MinecraftExtension = {
  modelId: string;
  textureDocuments: Array<{ slot: string; documentId: string }>;
  activeTextureSlot: string;
  pose?: Record<string, [number, number, number]>;
  animationId?: string;
};
```

Текстуры остаются обычными документами ядра (skin 64×64, elytra 64×32, item 16×16, atlas любого размера). Это позволяет открывать их во вкладках и переиспользовать все инструменты.

### 5.5 Импорт/экспорт

- Импорт `.bbmodel`, Bedrock `.geo.json`, Java block/item JSON.
- Импорт текстур PNG с привязкой к слотам.
- Экспорт PNG/атласа.
- Экспорт resource pack: `assets/<namespace>/textures/...` + `models/...` + `sounds` не нужны.
- Импорт старого `.mts` — через миграцию в Minecraft-плагине.

## 6. Форматы проектов

### Пиксель-арт

Новый формат ядра, например `.rsp` (или `.pxproj`):

```json
{
  "format": "rawsprite-project",
  "version": 1,
  "name": "sprite",
  "width": 64,
  "height": 64,
  "layers": [],
  "palettes": [],
  "settings": {},
  "extensions": {}
}
```

### Minecraft

Тот же контейнер + `extensions.minecraft`:

```json
{
  "format": "rawsprite-project",
  "version": 1,
  "width": 64,
  "height": 32,
  "extensions": {
    "minecraft": {
      "modelId": "elytra",
      "textureSlots": { "elytra": "layer-doc-id" }
    }
  }
}
```

Это позволяет открывать файл в обоих приложениях: RawSprite покажет текстуру и проигнорирует неизвестное расширение, RawSprite Minecraft восстановит модель.

### Миграция

- `.mts` v1/v2 (64×32) читается Minecraft-плагином и конвертируется в новый формат;
- ядро не обязано знать `.mts`;
- старые проекты продолжают открываться в Minecraft-редакторе;
- при сохранении старый `.mts` можно оставить как экспорт, но основной формат — новый.

## 7. UI и брендинг

- Общая Win9x-оболочка в `packages/editor-ui`.
- RawSprite: документы-спрайты, без вкладок «3D/UV», без Minecraft-панелей; палитра, слои, таймлайн кадров (позже).
- RawSprite Minecraft: те же вкладки + панель модели, UV, 3D, выбор модели, слоты текстур.

- Настройки: ядро хранит общие, плагин — `minecraft.*`.
- Иконки/имена:
  - `RawSprite` — новый идентификатор и иконка;
  - `RawSprite Minecraft` — текущий бренд/иконка;

## 10. Риски

1. **«Все модели»** — Java-сущности не data-driven; без курируемой библиотеки/конвертера полного автопокрытия не будет.
2. **Юридические ограничения** — модели/текстуры Mojang нельзя бездумно бандлить в публичный репозиторий. Нужны собственные/лицензированные ассеты или импорт из файлов пользователя.
3. **Производительность** — большие холсты и полные snapshot-истории; нужен лимит и затем дельта-история.
4. **Plugin API** — легко «протечь» внутренностям ядра; версионировать и держать узким.
5. **Два 3D-стека** — `skinview3d` и общий рендерер; лучше один общий, иначе двойная поддержка.
6. **Динамические плагины** — безопасность, CSP, подписи; не делать в v1.
7. **Дублирование UI** — вынести оболочку в `editor-ui`, иначе два аппа разойдутся.
8. **Миграция `.mts`** — старые файлы должны открываться; хранить тесты миграции.

## 11. Оставшиеся детали

1. **Расширение RawSprite**: предлагаю `.rsp`; `.mts` остаётся для Minecraft-проектов.
2. **Имя GitHub-репозитория**: `rawsprite`; переименование делает владелец GitHub.
3. **Название Minecraft-приложения**: `RawSprite Minecraft` (можно `RawSprite: Minecraft`).
4. **Анимации**: решение отложено; API плагина оставляет место для них.
5. **Старые `.mts`**: остаются импортом и, при желании, экспортом Minecraft-редактора.

## 12. Первые шаги после согласования

1. Создать workspace-каркас и перенести чистые `utils` в `packages/core` без изменения поведения.
2. Ввести `Document.width/height` и прогнать тесты на нескольких размерах.
3. Определить `plugin-api` типами и сделать no-op хост.
4. Подключить текущий `ElytraViewer` как первый плагин-адаптер, не удаляя функциональность.
5. Только после этого начинать новые форматы моделей; в v1 достаточно текущего плеера/элитр.

Главный принцип: сначала **ядро и размеры**, затем **границы плагина**, и только потом **модели**. Если начать с моделей, разделение придётся переделывать.
