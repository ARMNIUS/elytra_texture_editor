Дата: 2026-10-26. Ветка: `split-sys`, коммит `dab72fa`, рабочее дерево чистое.

> Статус на конец сессии: **B1, B2, B3, B4, B5 и B11 исправлены** (см. §8), добавлены
> `extensions` в проект и foundation plugin host. Остальные пункты остаются актуальными.
Проверено: `npm run typecheck` (успешно), `npm test` (27 файлов, **158 тестов**, успешно),

## 1. Что это за проект

RawSprite — два desktop-приложения на общем ядре, React 19 + TypeScript + Vite + Tauri 2:

```text
apps/rawsprite              RawSprite: 2D-редактор, без three/skinview3d
apps/rawsprite-minecraft    RawSprite Minecraft: то же ядро + Minecraft-плагин
packages/core               растр, слои, выделение, палитры, формат проекта (без React)
packages/editor-ui          Win9x/XP UI: канвас, палитра, слои, диалоги, файлы, стили
packages/editor-app         общая оболочка App.tsx (~1746 строк), состояние документов
packages/plugin-api         типы API + PluginHost v1 (реестры, lifecycle, события, storage)
packages/plugin-minecraft   ElytraViewer, MinecraftPreview, ModelPreview, загрузчики моделей
src/                        legacy-оболочка и 158 тестов (реэкспорты пакетов)
src-tauri/                  legacy Tauri-оболочка «Minecraft Texture Studio 0.12.0»
```

Модель данных: `DocumentState[]` (по документу: слои, активный слой, undo/redo, выделение,
zoom, skin, dirty, путь проекта) + глобальные clipboard/инструмент/цвет/палитры/шорткаты.
Пиксели — массив строк `#rrggbb[aa]`, композиция слоёв пересчитывается на каждый чих.
Проект — JSON `minecraft-texture-studio-project` версии 3 (ширина/высота, слои, настройки,
шорткаты, палитры, opaque `extensions`). `.mts` и `.rsp` — один и тот же контейнер, отличается только расширение.
Файлы в Tauri читаются/пишутся кастомными Rust-командами, диалоги — `tauri-plugin-dialog`.

Заявленное состояние (README, AI_CONTEXT, SPLIT_ARCHITECTURE): split выполнен, два установщика
собраны, следующий этап — редактирование импортированных моделей. Фактически split выполнен
частично: **plugin host v1 реализован, но UI-слоты панелей/оверлеев/preview ещё не
подключены**, Minecraft-код всё ещё зашит в оболочку, а часть заявленных возможностей не
работает (см. B6).

## 2. Критические баги

### B1 (P0). 3D-рисование и оверлеи на элитрах не работают из-за двух копий three.js — исправлено, см. §8

Симптом: включённое «Рисовать по модели» ничего не рисует; кисть/ластик/заливка/пипетка по
элитрам не срабатывают; «Сетка на модели» и «Границы геометрии» на элитрах не появляются.
При этом импортированные .bbmodel/.geo.json рендерятся и получают shader-сетку.

Причина:

- `ElytraViewer` импортирует `Mesh`/`Raycaster` из корневого `three` (0.186.1) и собирает
  меши крыльев через `object instanceof Mesh`:
  `../packages/plugin-minecraft/src/ElytraViewer.tsx#L78-L80`.
- `skinview3d@3.4.2` жёстко зависит от `three ^0.156`; npm ставит вложенную копию
  `node_modules/skinview3d/node_modules/three@0.156.1`. `npm ls three`:
  `skinview3d -> three@0.156.1`, остальное — `three@0.186.1`.
- В собранном бандле присутствуют обе ревизии (`"156"` и `"186"`), а
  `root.Mesh === nested.Mesh` даёт `false`.
- Как следствие `wingMeshesRef` пуст: `hitPixel()` рейкастит по пустому массиву
  (`...#L251`), а `gridLines`/`edgeLines` не создаются.

Это регрессия после обновления three до 0.186 ради `three-blockbench`/`@bedrock-viewer`:
раньше three был один, `instanceof` работал. CHANGELOG и README при этом продолжают
обещать «Direct 3D painting via UV raycasting» и сетку/границы на модели.

Что делать: как минимум заменить `instanceof Mesh` на duck-typing (`(object as Mesh).isMesh`)
и прогнать ручной smoke-тест 3D-покраски; проверить, что r186-`LineSegments` нормально
рендерятся внутри r156-сцены. Надёжнее — не добавлять объекты чужой версии three в сцену
skinview3d: рисовать UV-сетку шейдером на материалах крыльев (как `installModelGrid`), а
границы строить средствами skinview3d. Долгосрочно — изолировать skinview3d (риск №5 из
SPLIT_ARCHITECTURE) или заменить его единым рендерером.

### B2 (P0). Закрытие приложения сохраняет только активную вкладку — исправлено, см. §8

В диалоге «Закрытие приложения» кнопка «Сохранить» вызывает `saveProject()` для активного
документа и сразу уничтожает окно:
`../packages/editor-app/src/App.tsx#L1735-L1739`, `...#L1056-L1082`.
Если грязных вкладок несколько, изменения остальных теряются без предупреждения. Если
активная вкладка чистая, а грязные — другие, приложение может открыть диалог сохранения
чистой вкладки и затем выйти, потеряв остальное.

Что делать: «Сохранить все» — пройти по всем `dirty` документам, сохранить каждый (с
диалогом пути для новых), при отмене/ошибке прервать закрытие; либо явно писать в диалоге
«Будут сохранены только N из M вкладок». Добавить тест на multi-document close.

### B3 (P1). Закрытие последней вкладки в RawSprite создаёт 64×32 `.mts` — исправлено, см. §8

`performCloseDocument` при пустом списке создаёт документ с жёстко прописанным
`'Без названия 1.mts'` и размером 64×32:
`../packages/editor-app/src/App.tsx#L789-L791`.
Для `mode="rawsprite"` это неверное расширение и неверный размер по умолчанию (там 64×64).
Нужно использовать `projectExtension` и размеры режима.

### B4 (P1). Загрузка проекта ломает zoom — исправлено, см. §8

`applyProject` ограничивает zoom снизу двойкой и округляет:
`../packages/editor-app/src/App.tsx#L1112-L1114`.
Проект 2048×2048 сохраняется с `zoom ≈ 0.35` (вписать холст), а открывается с `zoom = 2`
(200 %) — холст в 4096 px, читать нельзя. Нужен диапазон как у редактора (0.05…2048) без
округления; добавить тест round-trip zoom.

## 3. Высокие баги и продуктовые разрывы

### B5 (P1). Импорт PNG и «Очистить текстуру» путают имя и путь проекта — исправлено, см. §8

- `handleImport` после импорта делает `setFilename(toPngFilename(file.name))`, но **не
  сбрасывает `projectPath`**: `../packages/editor-app/src/App.tsx#L1355`. Следующий Ctrl+S
  молча перезапишет старый проект по старому пути.
- `resetTexture` оставляет `projectPath`, меняя имя на «Без названия.rsp»:
  `...#L1364-L1376`. Ctrl+S снова пишет в старый проект.
- `toPngName` не срезает `.rsp`: `../packages/editor-ui/src/files.ts#L38-L41`; экспорт
  стартового «Без названия 1.rsp» даёт `Без названия 1.rsp.png`.

Нужно: не переименовывать документ при импорте в существующий проект (или спрашивать),
сбрасывать/подтверждать путь при «новой текстуре», единый helper для PNG-имени с `.rsp`.

### B6 (P1). Minecraft-плагин не покрывает заявленные скины и плащи

README обещает «skins, elytra, cape, UV guides and a live 3D preview», но:

- Для документа 64×32 канвас всегда грузится как **элитры**: `viewer.loadCape(..., { backEquipment: 'elytra' })`
  `../packages/plugin-minecraft/src/ElytraViewer.tsx#L193-L201`. Плащ (`cape`) выбрать нельзя —
  `backEquipment` захардкожен, UI переключателя нет.
- Для документа 64×64 (скин) канвас **не грузится вообще**: `loadSkin` вызывается только для
  импортированного файла скина (`skinUrl`), а не из пикселей документа
  (`...#L177-L191`). Рисуешь скин — 3D-модель не меняется.
- `hitPixel` разрешает покраску только при 64×32 (`...#L242-L245`), поэтому по скину 64×64
  рисовать нельзя, хотя кнопка «Рисовать по модели» активна.
- UV-разметка скина (64×64) в 2D отсутствует: `TextureCanvas` знает только элитры
  (`../packages/editor-ui/src/TextureCanvas.tsx#L56-L63`).
- Пресета «Новый скин 64×64» нет; `NewDocumentDialog` предлагает только квадратные пресеты.

Нужно: тип документа/слот текстуры (skin/elytra/cape), автоматический выбор preview по
размеру и слоту, `loadSkin(createTextureCanvas(...))` для скина, UV-оверлей как вклад
плагина, явное сообщение «3D недоступно для этого размера» вместо тихо устаревшей картинки.

### B7 (P1). Импортированная модель не привязана к документу и не сохраняется

`MinecraftPreview` хранит модель в локальном `useState`: `...#L12-L27`. Компонент один на
всё приложение, поэтому:

- импортировал модель в вкладке A, перешёл в B — модель осталась, но текстура уже от B;
- модель не сохраняется в проект и не восстанавливается;
- закрытие/открытие проекта не сбрасывает модель;
- нет привязки к `DocumentState`/`extensions`, нет слотов текстур.

Это и есть «next milestone» из README, но текущее поведение — не просто недоделка, а
кросс-документная утечка состояния.

### B8 (P1). Формат проекта не поддерживает данные плагинов, а настройки глобальны — extensions добавлены, см. §8

- **Extensions добавлены:** v3 теперь хранит opaque `extensions` в `DocumentState` и JSON,
  `applyProject` восстанавливает их. Плагин пока не использует это поле, но round-trip
  покрыт тестом. Остаётся разделить глобальные палитры/бинды и настройки проекта.
- `buildProjectFile` кладёт в проект глобальные `shortcuts` и палитры из localStorage
  (`...#L1029-L1034`), а `applyProject` при открытии **перезаписывает глобальные**
  localStorage-палитры и шорткаты (`...#L1137-L1148`). Открытие чужого проекта меняет твои
  палитры и бинды; это не «настройки проекта», а побочный эффект.
- `format` остался `minecraft-texture-studio-project` для обоих приложений; отдельного
  `rawsprite-project`/v1 с `extensions`, как в SPLIT_ARCHITECTURE, нет.

Нужно: v4 с `extensions` (непрозрачный JSON для плагинов), миграция v3, разделение
«настройки проекта» и «глобальные настройки приложения», сохранение палитр без затирания.

### B9 (P1). 2048×2048 заявлен, но производительность и формат этого не выдерживают

Горячие места:

- `TextureCanvas` перерисовывает **каждый пиксель** через `fillRect` при каждом изменении
  `pixels`: `../packages/editor-ui/src/TextureCanvas.tsx#L156-L170`. Для 2048² это 4.19 млн
  `fillRect` на каждый pointermove.
- `compositeLayers` каждый раз проходит W×H×слоёв и парсит цвета:
  `../packages/core/src/layers.ts#L65-L94`; `pixels` — `useMemo` от `layers`
  (`App.tsx#L376`).
- `paintPoints`, `floodFill`, `clearRegion`, `pasteRegion` копируют весь массив пикселей
  на каждую операцию; при 4.19 млн это десятки мегабайт на движение.
- История — полные снимки слоёв. `historyLimit = floor(4_000_000 / area)`
  (`App.tsx#L256`): для 2048² это **1** шаг undo, для 1024² — 3.
- Проект — JSON с пикселем-строкой: ~11–13 байт на пиксель; один слой 2048² — примерно
  50 МБ JSON, несколько слоёв — сотни МБ; `JSON.stringify(..., null, 2)` блокирует UI.
- `emptyLayerPixels` создаёт массив из W×H ссылок на каждый новый слой.
- `MinecraftPreview` считает `textureUrl = canvas.toDataURL()` на **каждое** изменение
  пикселей, даже когда модель не импортирована (`MinecraftPreview.tsx#L14-L17`); для 2048²
  это полноразмерный canvas + PNG-кодирование на каждый штрих.
- `ModelPreview` при изменении `textureUrl` заново грузит текстуру через `TextureLoader`
  для моделей с `updateTexture` (Bedrock/без встроенной текстуры)
  (`ModelPreview.tsx#L186-L190`, `modelLoader.ts#L58-L67`) вместо обновления
  `texture.image`/`needsUpdate`.
- `ModelPreview` крутит `requestAnimationFrame` всегда, даже когда панель скрыта
  (`ModelPreview.tsx#L85-L91`); skinview3d-вьюер тоже живёт в скрытой панели.

Это не «мелкие тормоза», а несоответствие заявленному лимиту 2048×2048. Нужны ImageData/
`putImageData`, композиция через offscreen canvas, dirty rects, дельта-история, сжатый/
бинарный формат проекта, обновление текстуры без перезагрузки, пауза рендера при скрытой
панели.

## 4. Средние баги и слабые места

### B10 (P1/P2). RawSprite всё ещё тянет данные Minecraft-плагина

`App.tsx` импортирует `defaultElytraPixels` напрямую:
`../packages/editor-app/src/App.tsx#L24`; `@rawsprite/app` при этом не объявляет
`@rawsprite/plugin-minecraft` в зависимостях (`../apps/rawsprite/package.json#L12-L17`).
В собранном RawSprite-бандле присутствуют все 206 уникальных цветов дефолтных элитр
(проверено по `dist`). README обещает «RawSprite does not import … Minecraft assets» —
данные элитр импортируются. Нужно, чтобы стартовый документ/дефолтные текстуры поставлял
плагин через хук/вклад, а не оболочка.

### B11 (P2). `.rsp` и подписи интерфейса — исправлено, см. §8

- `ShortcutsModal` пишет «Открыть проект .mts», «Сохранить проект .mts» даже в RawSprite:
  `../packages/editor-ui/src/ShortcutsModal.tsx#L77-L78`.
- `PalettePanel` экспортирует GPL с заголовком «Exported from Minecraft Texture Studio»
  (`PalettePanel.tsx#L94`).
- `resetTexture` даёт «Без названия.rsp» в RawSprite и «untitled-elytra.png» в Minecraft
  (`App.tsx#L1373`), без индекса вкладки.
- `toPngName` не знает `.rsp` (см. B5).

### B12 (P2). Minecraft-оверлеи в общем UI

- `TextureCanvas` рисует UV-разметку элитр для любого 64×32 при `showUv`
  (`TextureCanvas.tsx#L489-L501`) и подпись «UV: 22, 0 → 48, 22».
- `App` показывает пункт «Показать UV-шаблон» и передаёт `showUv` даже в RawSprite
  (`App.tsx#L1542-L1543`, `...#L1621`), где это не имеет смысла.
- `showFloorGrid` есть в состоянии (`App.tsx#L335`), но отсутствует в `ProjectSettings`
  (`...#L140-L154`) и не сохраняется/загружается, в отличие от остальных оверлеев.

Нужно: UV-оверлей — вклад плагина (`OverlayRegistry`), а не хардкод в editor-ui.

### B13 (P2). Undo/redo, dirty и merge

- `undo`/`redo` всегда `setDirty(true)` (`App.tsx#L494`, `#L516`): отмена до
  сохранённого состояния всё равно показывает «не сохранён».

  Нужен save-point в истории (id/индекс снимка) или сравнение с сохранённым снимком.
- История не хранит `selection`, `zoom`, `filename`, `projectPath`; после undo изменения
  размера холста selection/zoom/имя остаются от нового состояния. Для resize это заметно.
- `mergeDown` сохраняет `lower.opacity` и запекает в пиксели верхний слой, но не применяет
  прозрачность нижнего: вид стека меняется. Либо запрещать merge при opacity < 100, либо
  запекать обе прозрачности.
- Floating transform (перемещение выделения) не сбрасывается при undo/reset/закрытии
  вкладки; в этих путях возможна потеря/попадание пикселей не в тот документ. Нужен guard и
  commit/cancel перед сменой контекста.
- `exportPng`/`saveProject` используют `pixels` (без floating), а не `displayPixels`;
  сохранение в момент незавершённого transform теряет floating-слой.

### B14 (P2). Валидация и безопасность

- `skinUrl` из файла проекта принимается любой строкой (`App.tsx#L1110`) и уходит в
  `viewer.loadSkin`. Проект может заставить приложение запросить `http(s)://…` (нарушение
  «no remote services») или огромный data URL. Разрешать только `data:image/png` с лимитом
  размера.
- `parseProjectLayers` проверяет только `typeof pixel === 'string'`
  (`../packages/core/src/project.ts#L12-L30`), без проверки hex-формата, лимита длины строки,
  числа слоёв и общего размера. Аналогично нет лимитов на импорт PNG/модели/палитры —
  многомегабайтный файл парсится целиком в UI-потоке.
- В обоих `tauri.conf.json` `csp: null` (`../apps/rawsprite/src-tauri/tauri.conf.json#L24-L26`),
  а кастомные Rust-команды принимают произвольный путь
  (`../apps/rawsprite/src-tauri/src/lib.rs#L3-L16`) — для локального редактора терпимо, но
  несовместимо с будущими сторонними плагинами.
- `write_binary_file` передаёт PNG как `Array.from(contents)` (JSON-массив чисел) —
  `../packages/editor-ui/src/files.ts#L62-L65`; для больших файлов это лишние копии и
  замедление IPC. Синхронные `fs::write`/`read_to_string` в командах могут блокировать
  главный поток на больших проектах; лучше async + `spawn_blocking`.
- Нет error boundary: ошибка рендера/плагина роняет всё приложение в белый экран.

### B15 (P2). CI, релизы, документация

- `.github/workflows/build-windows.yml` собирает **legacy** root-приложение:
  `npm run build` → `npm run tauri build` (root `src-tauri`, productName «Minecraft Texture
  Studio» 0.12.0), артефакт — `src-tauri/target/...` (`../.github/workflows/build-windows.yml#L44-L58`).
  Два новых приложения CI не собирает и в релиз не прикладывает.
- В `apps/*/src-tauri/tauri.conf.json` нет `bundle.fileAssociations` для `.rsp`/`.mts`;
  открытие проекта из Проводника/ассоциации не работает.
- Иконки обоих приложений идентичны (одинаковый SHA-256 `icon.ico`), продукт в панели задач
  не отличить.
- Версии рассогласованы: root `package.json` 0.12.0, RawSprite 0.1.7, Minecraft 0.14.9,
  AI_CONTEXT «0.13.0», README «0.13 split», RELEASING «0.12.0».
- `docs/RELEASING.md` описывает старый продукт/версию/пути; `AI_CONTEXT.md` устарел и
  содержит неверные пути (`src/styles.css`, `src/components/ElytraViewer.tsx` «остаётся в
  приложении»). README местами переоценивает готовность (скины/плащи/3D-покраска).
- Vite-конфиги приложений не задают `manualChunks`; 1.57 MB одним чанком, three грузится
  сразу, хотя 3D можно лениво подгружать.

## 8. Журнал исправлений (B1 + B2)

### B1 — 3D-покраска и оверлеи элитр

- `collectMeshObjects` (`packages/plugin-minecraft/src/meshUtils.ts`) собирает меши по
  структурному флагу `isMesh`, а не через `instanceof Mesh`. Это устраняет зависимость от
  того, какая из двух копий three.js создала объект.
- Пиксельная сетка больше не строится как `LineSegments` из корневой three r186: она
  накладывается шейдером `installModelGrid` на материалы крыльев skinview3d (r156) с
  `preserveMaterial: true`.
- Границы геометрии строятся тонкими `BoxGeometry`-брусками через конструкторы меша и
  геометрии, принадлежащие skinview3d, поэтому рендерер r156 не получает чужие материалы.
- Проверено в Chromium/WebGL: включение сетки и границ не роняет приложение, клик по крылу
  меняет пиксель текстуры и помечает вкладку грязной (статус «Рисование»).
- Добавлен регрессионный тест `src/meshUtils.test.ts` на объекты «чужой» three.

### B2 — сохранение всех вкладок

- `saveDocument(document, saveAs)` сохраняет конкретный документ и обновляет только его
  `filename/projectPath/dirty` через `writeDocumentById`.
- `saveAllDirtyDocuments()` последовательно сохраняет все грязные вкладки и прерывается на
  первой отмене/ошибке.
- Закрытие приложения вызывает `saveAllDirtyDocuments()`; закрытие грязной вкладки —
  `saveDocument` именно этой вкладки, а не активной.
- Диалог закрытия показывает количество грязных проектов.
- Добавлены тесты `src/App.saveall.test.tsx`: две грязные вкладки сохраняются обе и только
  затем окно уничтожается; отмена второго сохранения не закрывает приложение.
- Проверки: `npm run typecheck`, `npm test` (**158 тестов**),
  `npm run build:rawsprite`, `npm run build:minecraft` — успешно.

### B3/B4/B5/B11 — мелкие фиксы

- `applyProject` восстанавливает zoom в диапазоне 0.05…2048 без старого минимума 200%.
- Импорт PNG переименовывает только ещё не сохранённый документ; у проекта с путём имя
